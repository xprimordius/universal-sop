## 🧩 PROTOCOL SYSTEMS (Functional Clusters — F10 + F11 Fusion Documented)

Protocols don't operate in isolation. Many work together as functional systems. The clusters below show which protocols are designed to fire together.

### 🎨 Visual System (F11 Fusion — Documented 2026-05-21)

These 3 protocols form a unified visual experience. They run together on every section. Reference any one of them = invoke all three.

| 🆔 | 🏷️ Protocol | 🎯 Visual Role |
|:---:|------------|---------------|
| SP.1 | **MagNet (Magnetic Visual Engagement Protocol)** | The overall visual standard — tables, emojis, scannable structure |
| SP.2 | **Door Scan (Door Scanning Pattern Protocol)** | The scanning funnel — emoji → brief → detail in every table |
| SP.8 | **Protocol Visibility Protocol** | Surface every protocol used — no hidden mechanics |

**Combined effect:** User can scan any output in 5 seconds and know exactly what protocols ran.

### 📊 Token System (F10 Fusion — Documented 2026-05-21)

These 2 protocols form a unified fuel management system. They are mathematically and functionally coupled.

| 🆔 | 🏷️ Protocol | 🎯 Token Role |
|:---:|------------|--------------|
| SP.3 | **TTE (Token Threshold Engine)** | The math — thresholds (GREEN <108K / YELLOW 108-130K / RED 130-141K / CRITICAL >141K theoretical), 59K reserve, budget enforcement |
| — | **LTM (Live Token Monitor)** | The display — `📊 LTM: 📝 Section: ~XK · 📦 Step: ~XK · ⏱️ Session: ~XK / 200K · 🔋 Remaining: ~XK · 🌱 GREEN` after every section |

**Combined effect:** AI knows where it stands on fuel + user sees it transparently. TTE without LTM = invisible math. LTM without TTE = display without meaning.

### 🪞 Self-Check System (Related — Not Fused)

These 3 are related but kept SEPARATE on purpose (different lenses).

| 🆔 | 🏷️ Protocol | 🎯 Lens |
|:---:|------------|--------|
| SP.10 | **SCC (Self-Compliance Check)** | "Did I follow my OWN SOP rules?" |
| SP.11 | **QAC (Quality Assurance Check)** | "Is the output STRUCTURALLY well-formed?" |
| EN.4 | **Pulse Check (Compliance Pulse Check)** | "10-second mechanical pre-send audit of Priority 10 items" |

**Why kept separate:** SCC = SOP rules. QAC = structure. EN.4 = mechanical 10-item gate. Fusing them would blur the lens distinction. (See FUSION_ANALYSIS.md F12 — CONDITIONAL fusion, deferred until Pulse Check proves reliable over 10+ outputs.)

### 📋 Wrap-Up System (F7 — EXECUTED 2026-05-21)

These 3 protocols form the unified Wrap-Up Block at end of every STANDARD/COMPLEX output. Formally clustered as a single mandatory section.

| 🆔 | 🏷️ Protocol | 🎯 End-of-Output Role |
|:---:|------------|---------------------|
| SP.9 | **FE (Foresight Engine)** | Predict next problems + solutions, priority-tagged (🔴/🟡/🟢) |
| SP.7 | **Insights Protocol** | Surface present-adjacent helpful context not explicitly asked |
| SP.13 | **SHR (System Health Report)** | Multi-dimensional scorecard with substantiated scores |

**Combined effect:** End-of-output transparency triple — Future (FE) + Present (Insights) + Past (SHR scoring what just happened).

**Formal Wrap-Up Block sequence (mandatory order):**
1. 📋 Conclusion table (Stage 5 — maps every prompt item to deliverable)
2. 📍 Timeline (T1 → T2 → T3... with status)
3. 📊 Final LTM (Live Token Monitor)
4. 🔮 **FE (Foresight Engine)** — minimum 3 items priority-tagged
5. 📊 **SHR (System Health Report)** — 6 dimensions scored
6. 📊 Execution Debt Counter (honest)
7. 📋 SP.8 Protocol Visibility — SubSOP Execution Report (all 20 protocols)

**Insights are interleaved within FE items** (e.g., FE item that surfaces an opportunity = Insight). Not a separate section.

### 🔁 Failure Tracking System (F8 — Identified, Not Yet Executed)

Related but currently separate.

### ⚡ Execution Gate System (F9 — REVIEWED 2026-05-21, KEPT SEPARATE)

Related but kept SEPARATE because of timing precision. F9 conditional fusion was REVIEWED and REJECTED — different enforcement points cannot be safely merged without losing timing precision.

| 🆔 | 🏷️ Protocol | 🎯 Timing | 🛡️ Why Separate |
|:---:|------------|----------|----------------|
| SP.15 | **EEP (Execution Enforcement Protocol)** | DURING execution — no future tense, proof required | Catches "I will do X" mid-output before it becomes false signal |
| SP.16 | **PCG (Prompt Completion Gate)** | PRE-SEND — every acknowledged item has execution proof | Final gate cross-checking original prompt items vs delivered |

**F9 Decision (2026-05-21):** Document the two-phase nature explicitly rather than merge. Merging would collapse "during" and "pre-send" into a single check, losing the DURING-execution catch that prevents acknowledge-not-execute pattern.

### 🪞 Self-Check System (F12 — REVIEWED 2026-05-21, KEPT SEPARATE BY DESIGN)

| 🆔 | 🏷️ Protocol | 🎯 Lens |
|:---:|------------|--------|

**F12 Decision (2026-05-21):** All three are PRE-SEND but cover different lenses. Merging would blur:
- SOP rules (SCC) vs structure (QAC) vs mechanical 10-item gate (EN.4)

- KEEP SEPARATE — F12 fusion rejected

### 📐 SubSOP Count (F6 — REVIEWED 2026-05-21, DOCUMENTATION ONLY)

**F6 Decision (2026-05-21):** The original proposal was to reduce 16 SubSOPs → 10 by clustering. Per FUSION_ANALYSIS, this risks recreating "remember 43 rules" cognitive overwhelm if reduced wrong.

**Resolution:** Clusters are now documented in this file (Visual System, Token System, Wrap-Up System, Failure Tracking, Execution Gate, Self-Check System) WITHOUT reducing the count of 16 SubSOPs. Each SubSOP remains independently invokable; clusters are mental groupings for cognitive efficiency.

**Effective result:** Cognitive load reduced via clustering. Mechanical count unchanged. Best of both worlds.

<summary><b>SP.1 — MagNet (Magnetic Visual Engagement Protocol)</b></summary>

### Full Name
**MagNet — Magnetic Visual Engagement Protocol**

### Acronym Origin
"Mag" (magnetic) + "Net" (network of visual cues). Originally MN.1-MN.4 in early drafts.

### Core Purpose
Make every output visually engaging and scannable so users can extract value in seconds without reading paragraphs.

### Scope (Where It Applies)
- Every section of every output
- Every table, header, list
- Every confirmation, conclusion, foresight block

### Sub-Components
| 🆔 | 🏷️ Sub-Rule | 📝 Detail |
|:---:|------------|----------|
| MN.1 | Emojis far left | Every table row starts with an emoji column on the left |
| MN.2 | Tables over paragraphs | Comparisons, lists, status reports → table format |
| MN.3 | Headers with emoji anchors | Section headers use emoji prefixes for visual landmarks |
| MN.4 | Scannable structure | Bullets, numbered lists, short sentences |

### When Triggered
Always-On. Every section of every output. No exceptions.

### Failure Mode If Skipped
Wall-of-text outputs. User has to read everything to find key points. Alan's #1 trigger: "too wordy" / "not coherent."

### Token Cost
~0 additional (structural, not content). Saves time downstream.

### Related Protocols
- SP.2 Door Scan (Door Scanning Pattern) — pairs with MagNet to create scanning funnel
- SP.8 Protocol Visibility — uses MagNet formatting for protocol naming

<summary><b>SP.3 — TTE (Token Threshold Engine)</b></summary>

### Full Name
**TTE — Token Threshold Engine**

### Acronym Origin
Pure description — Token (the budget unit) + Threshold (decision boundaries) + Engine (the math system).

### Core Purpose
Mathematical fuel budget so sessions don't crash mid-task. Math-based, not judgment-based.

### Scope
- Every output (tracking)
- Every session (cumulative)
- Every long-running task (forecasting)

### Sub-Components
| 🆔 | 🏷️ Threshold | 📊 Range | 🎯 Action |
|:---:|------------|---------|----------|
| GREEN | Healthy | <108K / 200K | Full operations, all SubSOPs active |
| YELLOW | Warning | 108-130K | Abbreviated validation, plan checkpoint |
| RED | Critical | 130-141K | Checkpoint NOW, cache all state, no new deliverables |
| CRITICAL | Emergency | >141K (theoretical only) | Emergency cache dump |

### The Math (Why CRITICAL Is Unreachable)
- 200K context window
- 59K emergency reserve (locked)
- 130K + 59K = 189K (still <200K)
- So if RED triggers at 130K and emergency reserve activates, we never hit 200K

### Companion: LTM (Live Token Monitor)
Visible after EVERY section showing:
- 📝 Section tokens
- 📦 Step cumulative
- ⏱️ Session cumulative / 200K
- 🔋 Remaining
- Status emoji (🌱 GREEN / 🟡 YELLOW / 🔴 RED)

### When Triggered
- Estimate BEFORE every output (in header)
- LTM after every section
- Status check every wrap-up

### Failure Mode If Skipped
Session runs out of fuel mid-task. Work gets lost. AI doesn't warn before crash.

### Token Cost
~200 tokens per LTM × ~8-10 sections = ~2K per output. Worth it.

### Related Protocols
- EN.1 Output Skeleton pre-places LTM blocks
- SP.10 SCC verifies LTM presence before send

</details>

<summary><b>SP.17 — SIR (System Improvement Reflection)</b> ⭐ NEW 2026-05-21</summary>

### Full Name
**System Improvement Reflection Protocol**

### Acronym Origin
**S**ystem **I**mprovement **R**eflection — pronounced "sir" — every output ends with a reflection on how the SOP system itself should improve, based on what was observed DURING this output.

### Status
✅ MANDATORY in `MANDATORY_TIGHT_LOOP.md` v1.1 (2026-05-21). Reference-only in full SOP UNIVERSAL_SOP_PROMPT.md until v1.4 incorporation.

### Purpose
**Every output ends with 1-3 system-improvement insights.** Distinct from SP.9 FE (which is *content* foresight — "what bug will surface next?"). SIR is *system* improvement — "what should the SOP/agents/scripts/architecture itself become next, based on what I noticed while producing this output?"

Per Alan (2026-05-21): "insights for improvement which should be in the SOP/agents right? every time the SOP ends with this? if not implement and save for future use for all."

Motivation: without SIR, improvement opportunities surfaced during real work are lost. SP.9 FE captures content-level next-steps. SP.13 SHR captures past-output scoring. Neither captures *system-level* reflection. SIR closes that gap.

### Scope
- Runs in: every `MODE: OUTPUT-STANDARD` or `MODE: OUTPUT-COMPLEX` output
- Runs in: `MODE: OUTPUT-QUICK` (abbreviated — 1 insight max)
- Skipped in: `MODE: CONVERSATION` (no SOP overhead)

### Format
```
💡 SIR — System Improvement Reflection (SP.17)
| # | 🏷️ Category | 💡 Insight | 🎯 Effort |
|:-:|------------|-----------|----------|
| 1 | <category> | <one-line system-level insight> | <S/M/L> |
| 2 | <category> | ... | ... |
| 3 | <category> | ... | ... |
```

Position: after the body, before the Pulse Check. (EN.1 Output Skeleton mandates this slot.)

### Categories (use the icon prefix)
- 🛠️ **structural** — SOP architecture changes (new SubSOP, new agent layer, fusion, etc.)
- 📋 **convention** — rule wording, format clarity, naming refinement
- 🪙 **token** — efficiency / budget improvements
- 🔧 **tooling** — scripts, hooks, automation, generators
- 🔄 **process** — workflow improvements (when to invoke what, ordering)
- 📊 **measurement** — better detection / observability / metrics

### Effort Labels
- **S** (small) — under 1 hour, single file
- **M** (medium) — 1-4 hours, multi-file
- **L** (large) — half-day or more, structural change

### Mandatory Items
- **Minimum 1 insight** per OUTPUT-STANDARD output
- **At least 1 of every 5 outputs** should be effort=L (encourages structural thinking, not just nibbling)
- **No duplicates** — if an insight has been surfaced in the last 5 SIR rows, skip it (cross-check via cache/SIR_LOG.md when implemented)
- **Actionable** — every insight must be implementable, not vague aspiration

### When Triggered
Always at end of OUTPUT-STANDARD / OUTPUT-COMPLEX. Pulse Check P6 enforces presence.

### Failure Mode If Skipped
The SOP stops evolving via in-session observation. All improvements come from explicit Alan-prompted rebuilds. Insights surfaced during real work are lost. **F.20** is the failure entry that motivated this protocol.

### Token Cost
~200-400 tokens per output (1-3 insights × ~70-130 tokens each).

### Related Protocols
- **SP.9 FE** — sibling. FE = content foresight ("what's next for the user?"). SIR = system foresight ("what's next for the SOP?"). Together they cover both lenses.
- **SP.12 HFR** — pairs. HFR captures *failures* during output; SIR captures *improvement opportunities* (some failures, some not).
- **SP.14 RPT** — pairs. If an SIR insight reflects a pattern that's recurred 2+ times, it should also be logged to FAILURE_LEDGER as RPT.
- **EN.1 Output Skeleton** — SIR is now part of the mandatory skeleton (between body and Pulse Check).
- **EN.4 Pulse Check** — P6 verifies SIR was surfaced.

### Optional Future Enhancement
`cache/SIR_LOG.md` — append-only log of every SIR insight across outputs. Enables: deduplication, pattern detection, prioritization, conversion to FAILURE_LEDGER entries when an insight recurs. (Filed as a Tier-1.5 follow-up; not blocking.)

</details>

### Full Name
**Output Skeleton (Structural Anti-Decay Mechanism)**

### Core Purpose
Pre-built template with mandatory sections + LTM placeholders. Fill-in-the-blank, not recall-from-memory. Solves attention depletion (DC.1) and "wrap-up gets dropped" (DC.4).

### What's In The Skeleton
| 🆔 | 🏷️ Section | 📍 Position |

| EN1.6 | Wrap-Up Block | End — Conclusion + Timeline + Foresight + SHR + Debt + SubSOP Report |
| EN1.7 | Footer line | Last line — version + repo + status |

### Why Structural Beats Behavioral
The previous fix ("remember to do LTM in wrap-up") relied on memory. Memory is what fails under attention depletion. EN.1 makes the wrap-up template ALREADY HAVE the LTM placeholder — AI fills in the number, can't "forget" to add the section.

### When Triggered
Every output. Foundational.

### Related Protocols
- All wrap-up SubSOPs (SP.9-SP.13) live inside EN.1
