What is the Universal SOP?

A portable prompt + supporting files that force any Claude session (chat or Code) to produce traceable, accurate, auditable output every time. It evolved from the APW (Ascend Prime Wealth) course-building project — when course-building demanded reliability, the SOP got built. The SOP is now mechanically complete and shippable (MIT licensed) as STANDALONE_SOP.md.

What problem does it solve?

Three failure modes the SOP prevents:

  • Compliance decay over a long session — without anti-decay (EN.1-EN.4), outputs lose required sections by output #4-6.
  • Fabrication + theatre — without honest-numbers enforcement (P1 + N/M marker), AI invents specific times, percentages, etc.
  • Rubber-stamping — without QC + Meta-Verifier, the audit layer claims PASS without actually verifying.

Per F.19 (the meta-failure): rules implemented as conventions decay. Rules implemented as architecture (scripts + hooks + sub-agents) hold.

🧩 All 16 SubSOPs (SP.1 – SP.16)

⭐ marks the 6 protocols mandatory in MANDATORY_TIGHT_LOOP.md (Tier 1 of F.19). The other 10 are reference-only for operational use.

VISUAL SP.1 MagNet (Magnetic Visual Engagement Protocol)

Purpose: The visual standard — tables, emojis, scannable structure. Always-on. Prevents wall-of-text outputs.

Sub-rules: MN.1 emoji-first columns · MN.2 emoji-leftmost dedicated column · MN.3 ≤ 7 rows per table without break · MN.4 alternating row shading where supported.

Failure mode if skipped: Wall-of-paragraph outputs that Alan dislikes; cognitive scan-time skyrockets.

Origin: R1 in v1.0 (Mar 31). REPEAT × 3 (F.1).

VISUAL SP.2 Door Scan (Door Scanning Pattern Protocol)

Purpose: Emoji → brief → detail funnel in every table. Pairs with MagNet (F11 fusion).

Mechanic: Every table row starts with an emoji-only cell (the "door"), then a 1-3 word brief, then detail. Reader can scan emojis to skip to relevant rows.

TOKEN SP.3 TTE (Token Threshold Engine)

Purpose: Token budget math with thresholds.

Thresholds (200K window): 🟢 GREEN <108K · 🟡 YELLOW 108-130K · 🔴 RED 130-141K · 🆘 CRITICAL >141K (theoretical) · 59K reserve.

Pairs with: LTM (Live Token Monitor — the per-section display).

Origin: F.2 (REPEAT × 4) — Alan kept asking for token tracking that wasn't activated.

PROCESS SAFETY SP.4 SCP (System Change Protocol)

Purpose: Safe modification of the SOP itself. Version bump + backup + cross-cache update.

Triggers: Any change to UNIVERSAL_SOP_PROMPT.md, SESSION_START.md, or core agents.

Steps: (1) Backup → (2) Edit → (3) Update version stamp → (4) Cross-cache update (SESSION_STATE + BACKUP_LOG) → (5) Log in CONTINUATION.

PROCESS SAFETY — MANDATORY TIGHT LOOP SP.5 FSP (Fidelity Substantiation Protocol)

Purpose: Every claim has cited evidence. No fabrication.

Validator check: VL.2 — output's factual claims must have file paths, command outputs, log rows, or explicit "approx/N/M" qualifier.

Common violations: "The script passed" without showing the log. "Took 5 minutes" without timing source (should be N/M).

PROCESS SAFETY — MANDATORY TIGHT LOOP SP.6 IAC (Intent Alignment Check / Understanding Check)

Purpose: Restate user's question as a table BEFORE executing. Catch misinterpretation early.

Format: Table with columns "Your words" and "My interpretation" — at least 1 row per distinct ask.

Validator check: VL.1.

FORESIGHT SP.7 Insights Protocol

Purpose: Surface present-adjacent helpful context not explicitly asked. Part of F7 Wrap-Up cluster (with SP.9 FE + SP.13 SHR).

Position: Interleaved with Foresight items at end of output, not a separate section.

VISUAL SP.8 Protocol Visibility Protocol

Purpose: Name every protocol used in the output. No hidden mechanics.

Format: SubSOP Execution Report at end (per F.11 truncation fix → one row per protocol, full names mandatory, <details> expandable).

FORESIGHT SP.9 FE (Foresight Engine)

Purpose: Predict next problems + solutions, priority-tagged (🔴 critical / 🟡 medium / 🟢 nice-to-have). Part of F7 Wrap-Up cluster.

Minimum: 3 items per output (STANDARD or COMPLEX).

SELF-CHECK SP.10 SCC (Self-Compliance Check)

Purpose: "Did I follow my OWN SOP rules?" Different lens from QAC (which checks structural form).

Kept separate from SP.11 QAC + EN.4 Pulse Check per F12 fusion analysis — each is a different lens.

SELF-CHECK SP.11 QAC (Quality Assurance Check)

Purpose: "Is the output STRUCTURALLY well-formed?" — sections present, tables formatted, headers right.

Now embodied by: The new QC agent in the F.19 chain (Layer 3).

HONEST FAILURE — MANDATORY TIGHT LOOP SP.12 HFR (Honest Failure Report)

Purpose: When something failed (visible to user or self-detected), produce root cause + permanent fix IN THE SAME OUTPUT. No "I'll fix it next time."

Format template:

🚨 HFR — Honest Failure Report
Entry ID: F.X
Type: REPEAT / FAILURE
What failed: …
Root cause: …
Permanent fix (structural): …
Verified in this output by: …

Validator check: VL.3.

REPORTING SP.13 SHR (System Health Report)

Purpose: Multi-dimensional end-of-output scorecard with substantiated scores. Part of F7 Wrap-Up cluster.

Dimensions: Fidelity to user's question, honest numbers, solution concreteness, output-level SOP compliance, wall-clock time per section (often N/M).

HONEST FAILURE SP.14 RPT (Repeated Prompt Tracker)

Purpose: Catch when user asks 2+ times — signals an unenforced rule. Triggers HFR (SP.12) for permanent structural fix.

Logged to: cache/FAILURE_LEDGER.md (was cache/RPT_LOG.md until F8 fusion).

EXECUTION — MANDATORY TIGHT LOOP SP.15 EEP (Execution Enforcement Protocol)

Purpose: Execute, don't acknowledge. No future tense. Show proof of action in the message that promises it.

Common violation: "I'll create that file" without showing the file creation. "Will commit next" without the commit.

Validator check: VL.4.

EXECUTION SP.16 PCG (Prompt Completion Gate)

Purpose: Pre-send check that every item in the user's prompt has execution proof. Acts as the final gate before sending.

Position: Runs alongside EN.4 Pulse Check before any send.

REFLECTION — MANDATORY (NEW 2026-05-21, F.20 fix) SP.17 SIR (System Improvement Reflection)

Purpose: Every output ends with 1-3 SYSTEM-level improvement insights surfaced DURING the output. Distinct from SP.9 FE (which is content foresight). SIR is system improvement — "what should the SOP/agents/scripts itself become next?"

Per Alan (2026-05-21): "insights for improvement which should be in the SOP/agents right? every time the SOP ends with this? if not implement and save for future use for all."

Categories: 🛠️ structural · 📋 convention · 🪙 token · 🔧 tooling · 🔄 process · 📊 measurement

Effort labels: S (under 1h) · M (1-4h) · L (half-day+)

Format: table with #, category, insight (one-line, actionable), effort. Position: between body and Pulse Check.

Mandatory: minimum 1 insight per OUTPUT-STANDARD; at least 1 of every 5 outputs is effort=L.

Failure mode if skipped: The SOP stops evolving via in-session observation. All improvements come from explicit Alan-prompted rebuilds. F.20 entry documents this exact gap.

Validator check: VL.7. Pulse Check item: P6.

Append-only log: cache/SIR_LOG.md ⭐ NEW 2026-05-21 — every SIR insight logged with date/device/commit/category/effort/status/recurrence for cross-output pattern detection.

SYNC CONFIRMATION — MANDATORY (NEW 2026-05-21, F.21 fix) SP.18 SSC (Sync Status Confirmation)

Purpose: Every file-modifying output ends with explicit confirmation/records of GitHub + Obsidian + cross-device sync state. Per-channel table answering: did the commit happen? did the push land? is the working tree clean? is Obsidian state OK? do other devices need to pull?

Per Alan (2026-05-21): "incorporate into the global SOP that at the end it lets us know if the changes were updated/uploaded to the github & obsidian or not. need confirmation or records for every output end."

Channels reported:

  • Git branch
  • Last commit (SHA + subject)
  • Git push to origin/main (status + timestamp)
  • Distance local ↔ origin (0/0 = in sync)
  • Obsidian vault (present + no conflict files)
  • Cross-device propagation (mac-main + others — pending pull / in sync / diverged)
  • Backups created (count this output)
  • BACKUP_LOG total rows
  • SIR_LOG total rows
  • Device + timestamp (audit trail)

Status codes: ✅ confirmed · ❌ failed (with reason) · ⚪ N/A · ⚠️ partial · ⏳ pending

Position: AFTER Pulse Check, as the FINAL block of every file-modifying output.

Backing script: scripts/sync_status.sh ⭐ NEW 2026-05-21. Reads git state + Obsidian dir + cache row counts + device identity. AI invokes + surfaces output verbatim.

Failure mode if skipped: Sync state opaque. User has to ask "is it on GitHub?" repeatedly. Silent push failures hide. Multi-device drift undetected. F.21 entry documents this exact gap.

Validator check: VL.8. Pulse Check item: P7.

🛡️ All 4 Ensurance Components (EN.1 – EN.4)

The anti-decay layer. Solves F.9 (compliance decay over 4-6 outputs). EN.1 + EN.4 are mandatory in the F.19 tight loop.

MANDATORY TIGHT LOOP EN.1 Output Skeleton (Structural Anti-Decay Mechanism)

Purpose: Mandatory sections never silently dropped. Skeleton forces all components every output.

Mechanism: Output template with required sections (STEP → UC → body → LTM → Pulse Check → Wrap-Up). Missing sections become visible as empty headers, prompting fix.

Validator check: VL.5.

ANTI-DECAY EN.2 Priority 10 (Cognitive Load Reduction)

Purpose: Top-10 attention rules, surfaced every output. Reduces what Claude has to "remember" — the 10 most important rules are explicit.

ANTI-DECAY EN.3 Checkpoint Cycle (Attention Reset)

Purpose: Re-anchor after long sections. Prevents drift in multi-thousand-token outputs.

Mechanic: After every ~3 sections, a checkpoint marker that restates the macro/micro goal.

MANDATORY TIGHT LOOP EN.4 Pulse Check (Compliance Pulse Check)

Purpose: Pre-send mechanical sweep. Visible. Scored.

Original (full SOP): 17 items (P1–P17).

Reduced (MANDATORY_TIGHT_LOOP v1.0 per F.19 Tier 1): 5 items (P1-P5).

Reduced v1.1 (per F.20 2026-05-21): 6 items — adds P6 for SIR.

  • P1 Honest numbers; N/M for unmeasurable
  • P2 Tables for comparisons
  • P3 Headline-first
  • P4 Inference vs fact marked
  • P5 Promise = deliver in same message
  • P6 ⭐ SIR surfaced (SP.17 — 1-3 system-improvement insights with category + effort)

Score: X/6 (v1.1) or X/5 (v1.0 grandfathered). Pass criterion: 6/6 (or 5/5) for ship; one item down with brief acknowledgment is acceptable; ≤ 4/6 → fix.

Git Hooks (2)

.githooks/pre-commit · F.16 + F.19 chain invocation

Runs in order: append_only_check → compliance_check → device-identity verify → verifier → validator → qc → meta_verify.

Append-only is BLOCKING (commit refused if cache file shrinks). Others are warnings-only (per F.19 Tier 1 stabilization).

Bypass: git commit --no-verify + must include HFR justification in commit message OR QC will flag in next commit.

.githooks/pre-push · F.18 — multi-device live sync

Fetches origin before push. If remote ahead, BLOCKS push and tells user to run bash scripts/safe_push.sh. Prevents the rejected-push-then-pull-rebase cycle that happens in multi-device parallel work.

The 7 Golden Rules (MULTI_DEVICE_GIT_PROTOCOL.md)
  1. ALWAYS pull before work
  2. ALWAYS commit + push after work
  3. NEVER force-push
  4. NEVER rewrite history (no rebase / reset --hard / --amend after push)
  5. ONE device at a time for active work (no simultaneous edit without push between)
  6. APPEND-ONLY for history files (cache/SESSION_STATE, BACKUP_LOG, FAILURE_LEDGER, CONTINUATION) — F.15
  7. NEVER delete files (use cache/legacy/archived_* prefix instead) — F.15
Universal Backup & Preservation Rule (SESSION_START.md)

Repo-wide rule. Applies to ALL files in this repo, not just cache. 7 sub-rules:

  1. NEVER delete existing files
  2. Backup BEFORE every modification
  3. Timestamped filename + device identity
  4. Log every backup in cache/BACKUP_LOG.md
  5. Applies to ALL files
  6. Cross-device inheritance (lives in repo, not local config)
  7. Device identity is non-optional
Conflict resolution playbook (4 scenarios)

A. Cache file conflict (most common): KEEP BOTH blocks, renumber. Cache files are append-only — never resolve by picking one side.

B. SOP file conflict: Decision tree — same section? keep newer logically. Different sections? merge both. Conflicting structural changes? request keep more comprehensive + log F.X entry.

C. Mistake / want to undo: Use git reset --soft HEAD~1 (keeps changes) BEFORE pushing. After push: never rewrite.

D. Catastrophic / force-push recovery: Use git reflog + --force-with-lease. Better: never force-push in the first place.

  • Tier 3 ⏳ STAGED: Outputs are files, not chat replies. Convention becomes architecture via pre-commit gate.
