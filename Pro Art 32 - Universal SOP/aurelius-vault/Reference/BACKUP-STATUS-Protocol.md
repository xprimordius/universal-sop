# BACKUP-STATUS Protocol — "Am I backed up, where, when, can I restore?"

Linked: [[index]] · [[Aurelius-Master-SOP]] · [[Multi-Device-Sync-Protocol]]

**Status**: Active (introduced Op 44, 2026-05-22)
**Authority**: Mandatory at end of every op writeup AND end of every conversation response that produces persistent state. Optional for read-only / Q&A responses.
**Owner**: `backup_status.py` script does the probe; Claude renders the block.

---

## The principle

> Every time work persists to disk or git, the user must SEE proof of redundancy + restore commands at end of the response. No silent "trust me, it's backed up."

This sits alongside the 5 mandatory protocols (Master-SOP, PROVE-IT, GOLD-PATH, EOE, Multi-Device-Sync) as the visibility surface for the safety net Multi-Device-Sync builds. Multi-Device-Sync makes sure pushes are safe; BACKUP-STATUS makes sure the user can SEE that they are.

---

## The 4 redundancy layers (what gets probed)

| # | Layer | What "OK" means | Probe |
|---|---|---|---|
| 1 | **Local disk** | Vault + agent-stack directories exist and are writable | `Path.exists()` + sentinel touch/unlink |
| 2 | **Local git** | `.git/` present, HEAD SHA known, clean or dirty count surfaced | `git rev-parse HEAD` + `git status --porcelain` |
| 3 | **GitHub remote** (xprimordius) | `git ls-remote origin HEAD` matches local HEAD | one network call per repo |
| 4 | **Public gist** (protocol mirror) | `gh gist view <ID> --files` returns expected file list | `gh` CLI authoritative call |

If any layer reports not-OK, the status block shows ✗ or ⚠ and includes the reason.

## The required output block format

At end of every op writeup AND every response that persists state, render:

```
🛡️ **BACKUP STATUS** · Op N · YYYY-MM-DD HH:MM UTC (HH:MM:SS local)

**vault**:
  ✓ Local disk   `C:\aurelius\aurelius-vault`
  ✓ Local git    HEAD `SHA` (N uncommitted) — _last commit message_
  ✓ GitHub       `SHA` — in sync

**agent-stack**:
  ✓ Local disk   `C:\aurelius\aurelius-agent-stack`
  ✓ Local git    HEAD `SHA` (N uncommitted) — _last commit message_
  ✓ GitHub       `SHA` — in sync

**Public protocol gist**:
  ✓ N files synced — https://gist.github.com/xprimordius/<gist-id>

**Device**: `Aurelion-Primary`
**Sync-Log**: N push events recorded

**Restore commands**:
git checkout <SHA> -- <path>          # restore single file
git reset --hard <SHA>                # roll repo back
git fetch origin && git reset --hard origin/main   # roll forward from GitHub
```

**Generated by**: `python backup_status.py` (full) or `--brief` (one-liner) or `--json` (machine-readable).

## Multi-device sync state — how it works today

Aurelius's multi-device model (from Multi-Device-Sync-Protocol, the push-safety rules):
1. Per-device git identity via `~/.aurelius-device-id` — every commit signed `Alan @ <device-name>`
2. `safe_push.py` always pulls + rebases before pushing (no force-pushes)
3. `Sync-Log.md` is append-only, records every push: time + device + repo + SHA + message
4. GitHub xprimordius is the canonical convergence point

**BACKUP-STATUS surface**:
- Device ID printed in every status block (which device produced the push)
- Sync-Log row count printed (forensic trail length)
- GitHub remote HEAD compared to local HEAD per repo (shows divergence if another device pushed first)

**What backup_status.py does NOT do (yet)**:
- Probe OTHER devices' clones (no centralized device registry beyond Multi-Device-Sync-Protocol's table)
- Detect if another device has uncommitted local changes
- Trigger pull on remote devices

These are Op 45+ candidates for full multi-device visibility.

## Version numbering scheme

Aurelius uses **op number as the version**. Examples:
- `Op 43` = working through Op 43 changes
- `Op 43 @ eb6453b` = Op 43 state at git SHA eb6453b
- `v0.43` (informal) = version 0.43 of Aurelius (we have not yet declared 1.0; per Master-SOP §9 we're at 11/15 DoD ≈ 73%)

Every commit message includes the op number (enforced by Pulse Check 2.0 item 8: "Commit message references op number + change list").

Restore by op number:
```bash
# Find the SHA for a given op
git log --oneline | grep "Op 38"

# Roll back to that SHA
git reset --hard <SHA>
```

## Restore commands (canonical)

| Goal | Command |
|---|---|
| Restore one file at a past op | `git checkout <SHA> -- <path>` |
| Roll whole repo back to a past op | `git reset --hard <SHA>` (destructive — backup first) |
| Roll forward to GitHub current | `git fetch origin && git reset --hard origin/main` |
| Recover from broken local state | `git fsck && git reflog` — find lost commits |
| Restore from another device | Clone fresh: `gh repo clone xprimordius/aurelius-vault` |
| Restore from settings backup | `cp ~/.claude/settings.json.pre-opN-prune.bak ~/.claude/settings.json` |
| Restore deleted file | `git log --all --diff-filter=D --name-only --pretty='%h %s'` then `git checkout <hash>^ -- path` |

## Bug-check compatibility

When debugging a regression, the standard procedure:
1. Run `python backup_status.py` to confirm current state is recorded
2. Identify the suspect op number: `grep "## Operation" vault/Reference/Operations-Log.md`
3. Compare current behavior to pre-op state: `git diff <SHA-of-op-N-1>..<SHA-of-op-N> -- <suspect file>`
4. If regression confirmed, roll back ONE op at a time: `git reset --hard <SHA>`
5. Re-test
6. If fixed, the offending op is identified — file F-NNN entry in Failure-Ledger
7. Forward-fix: cherry-pick subsequent ops one at a time: `git cherry-pick <SHA>`

The Sync-Log + Operations-Log + per-op SHAs make this surgical, not guesswork.
